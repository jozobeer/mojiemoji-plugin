# Mojiemoji フレーバーガイド

機械的な配置(どの surface のどのモードで使うか) は `SKILL.md` で扱う。
このファイルは **テイスト層** — スタンプが本当に「決まる」ための条件と、
逆に「ノイズ」になる条件をまとめる。フォントや色を選ぶ前にこちらを読むこと。
そちらより重要。

## 原則

### 1. スタンプは修飾語・判定語にあてる、名詞には絶対あてない

スタンプは別の語にムードを足すためのもの。情報そのものを置き換えてはダメ。

- 良い: `【マジで】やばい【バグ】ですね` — 副詞 + 判定語スタンプ
- 良い: `動くけど【微妙】` — 判定語スタンプ
- 悪い: `【関数】をリファクタ` — 名詞スタンプはムードを足さない、単なるノイズ
- 悪い: `【API】を叩く` — 事実情報、絶対スタンプしない

### 2. 感情のピボットに置く

スタンプは、文が「事実」から「判定」へ、あるいは「前振り」から「リアクション」
へと折れる場所に置く。

- `通ったが【納得いかない】`
- `動くけど【謎】`
- `直ったけど【真因不明】`

### 3. 前振りではなくオチに置く

オチに 1 スタンプの方が、前振りに 3 スタンプより強い。コメディのタイミング。

- 良い: `調べたら【完全に別案件】でした。`
- 悪い: `【調べたら】【完全に別案件】でした。` — 前振りにスタンプ、エネルギーの無駄遣い

### 4. 逆接マーカーの直後はゴールデンスロット

否定・逆接・反転は、その先のスタンプを際立たせる助走になる。

- `〜だけど【正直】微妙`
- `〜したのに【なぜか】通る`
- `〜のはずが【まさかの】成功`

### 5. 自虐 > 謝罪

自分のミスにスタンプを当てる方が、謝罪より強くて重くない。

- `【やらかし】直します` > `申し訳ありません、修正します`
- `【誤読】でした` > `勘違いしていました`
- `【完全に草】` > `失礼しました笑`

### 6. レビューの締めには判定スタンプ

レビューブロックの末尾にスタンプを置くと、それが全体の結論を担う。

- `このPRは……(議論)…… 結論: 【マージして良し】`
- `…動作確認しました。【OK】`

## スタンプ禁止

| 領域 | 理由 |
|---|---|
| API 名、ファイルパス、識別子 | 検索性・引用性を損なう |
| 数値、バージョン、日付 | 情報密度が高い、スタンプで値が読めなくなる |
| 障害・セキュリティ報告の謝罪本文 | 真剣さが揺らぐ |
| セキュリティ指摘・リスク記述 | トーンが合わない、読み手が指摘を割り引いて受け取る |
| 要件・受入基準 | 仕様は文字通りに残す |
| 法務・コンプライアンス文 | 同じ理由 — 絶対に飾らない |

## 量のルール

| コンテキスト | inline 最大数 | block 最大数 |
|---|---|---|
| 本番コードのフォーマルなレビュー | 0–1 | 0–1 |
| 通常の PR レビュー / チーム issue | 段落あたり 1–2 | セクションあたり 1 |
| 社内チャットライクなスレッド | 2–3 | 数個 |
| 意図的に「うるさめ」モード(ユーザー指定) | 上限なし | 上限なし |

デフォルト: ユーザーが明示的に「うるさめ」(「もっと盛って」「うるさめで」
「祭り」など) を指示しない限り、formal〜regular を仮定する。

## スタンプ前のクイックチェックリスト

1. 対象は **修飾語・判定語・感情** か?(名詞ではないか?)
2. 文の **ピボット or オチ** に置いているか?
3. スタンプを外したら文として情報が欠けるか? もし欠けるなら情報を
   置き換えてしまっている — 退避すべし。
4. surface のトーンは適切か?(障害対応・法務・セキュリティクリティカル
   ではないか?)

どれか 1 つでも "no" ならスタンプはやめる。よく置かれた 1 つの方が、
凡庸な 3 つより強い。

## 文法セーフティチェック(埋め込みモード)

スタンプを **inline 埋め込み** (文中の語を置換、装飾用の独立行とは別物)
として挿入する前に、以下を確認する:

> スタンプの `alt` テキストでスタンプを置き換えて文を音読する。自然な
> 日本語として通るか?

通らないなら、その埋め込みは壊れている — スタンプを外すか、本文の下の
装飾行に退避する。

| 例 | 通るか | 判定 |
|---|---|---|
| `カラムが【グッド】で存在する` | 「カラムがグッドで存在する」 — 副詞スロットは `順調に` / `ちゃんと` が要る、名詞判定の `グッド` ではダメ | 壊れている — 外す |
| `カラムが【存在】する` | 「カラムが存在する」 — サ変動詞 `存在` がスロットを満たす | OK |
| `…したい【マジで】【大事】。` | 「…したいマジで大事。」 — 文がくっつき、どこで切れるか読み手にわからない | 壊れている — `→ 【マジで】【大事】` の装飾行に退避 |
| `通ったが【納得いかない】` | 「通ったが納得いかない」 — 接続が自然 | OK |

このルールは **飽和モード**(「マシマシ」「二郎系」「絵文字入れまくって」)
でも適用される。飽和は「スタンプ可能な語の範囲」を緩める(`DB`、`E2E`、
`仕様` といった事実語も OK になる) が、**埋め込みが文法的に成立する**
という要件は緩めない。

## 埋め込み vs 装飾

`inline` モードは、ソースは同じ形でもレンダリング結果が大きく異なる
2 パターンを内包している:

| パターン | 場所 | ルール |
|---|---|---|
| **埋め込み** | 文中 | スタンプが語を置換する。文法セーフティチェックを通すこと |
| **装飾** | 本文の下に独立行 | スタンプは文法的役割を持たず、ムードを足す。`→ ` を前置するか `【...】` で囲む |

**本文の文末に装飾を付け足してはダメ。** 末尾スタンプは埋め込みと
視覚的にくっつき、文がどこで終わるか読み手にわからなくなる。セクション
見出しの末尾装飾は OK(見出しは本文と視覚的に分離されている)。

```markdown
<!-- 悪い: 本文の末尾に装飾 -->
…してほしい <マジで> <大事>。

<!-- 良い: 装飾は専用行 -->
…してほしい。

→ <マジで> <大事>

<!-- 良い: 見出し末尾の装飾 -->
## デプロイ順序 <大事>
```

## 飽和モード

ユーザーが明示的に最大「うるさめ」を要求した場合 — 「マシマシ」「二郎系」
「盛って」「絵文字入れまくって」「saturate」 — 以下を緩める:

- 事実語(`DB`、`E2E`、`仕様`、`要件`、`対称`、`判断`、`基準`)も
  文法的に収まれば埋め込み OK。
- AC チェックリスト・調査リストにもスタンプを乗せて良い。
- 「1 文あたり inline 最大 2 個」 のルールも緩む — 文法的に成立する範囲で
  好きなだけチェーン可。

絶対に動かないもの:

- 上記の文法セーフティチェック。
- 装飾は独立行、本文末尾には付けない。
- コード、パス、識別子、バージョン文字列、リンク — 絶対スタンプしない。
- ダークモードセーフな色(Tailwind 300–500 レンジ、特に 300–400 を優先;
  SKILL.md § Dark-mode-safe color palette)。
- animation 必須、`spin` は使わない(無効値、無音で静止画になる)。
  `bakusan` は **block 専用** — 放射バーストが inline サイズでは
  letterform を潰す(`parameters.md` § Valid animation values を参照)。
  その他は `kira` も含めて inline で歓迎。
